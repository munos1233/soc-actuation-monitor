# 属性准入对事务证据是不完备的

**Attribute Admission Is Incomplete for Transactional Evidence**

**作者：匿名作者**

---

## 摘要

一次处置写——关闭一张工单、下发一条厂商命令、变更一个集群——只有当最后一次写是一个规划器（proposer）无法伪造的特权、谓词在同一事务或准入评审中重建、且观察不能凭空产生效应时，才被中介化（mediated）。我们称这种属性形态的准入（OPA、Gatekeeper、IAM 条件）请求并检查属性，因此 TEI 在 close 与 bind 两方面是不完备的：外部策略引擎能在一条写路径上评估的 16/45 个决策点恰好遗漏了 TEI 坚持要求同处一处的那四个。我们在两条写路径上实例化 TEI。在 SOC 工单上，四条证据谓词加一条 PostgreSQL 角色拆分把 47/57 边界注入降到 0/57（pseudo-live 为 0/29）；一个规划器登录持有这些特权语句的特权行就会被拒绝（SQLSTATE 42501；owner 列为 12/12 owner）。签名请求属性（signed_attribute）保留了 OPA 侧的 16/45 不完备残差：完整性在 A0 上不是一个非规划器事实，在非提案事实上也不是。kind K8s lab 上的 CEs 用真实 CVE- 与文献映射的案例——不复现于原始产品、不改写 A0–A5 夹具——按朴素/属性/TEI 三臂打分；8 个 real-API 案例加 3 个 tei.lab 案例分别列表。Java TLC 在有限片（10800 个不同状态，next 下无对策）上给出无反例。TEI 与 Gatekeeper 有同一视图：CloseAccepted 与 PlannerForgedFingerprint→DispatchAccepted 这两个 CEs，TEI 单视图与 Biba 的"安全即可信"模型一样有缺陷。A1 与 A5 两列改进为 37/45。TEI Pair 是一个同视图检查：只读 planner 可写列的闭包/CE。

- **CCS 概念分类**：安全与隐私 → 系统安全；访问控制。
- **关键词与短语**：完全中介、准入控制、完整性、工单关闭、失败闭合中介（fail-closed mediation）。

## 1 引言（Introduction）

一条以处置告终的 SOC（安全运营中心）流水线——隔离这台主机、封掉这个账号、下发这个厂商处置、把工单置为 CLOSED——继承了这条流水线前一步的性质：**输出是对机构事故记录的一次变更**，而非对世界的一次改变。一个幻觉式的摘要，说一个人类分析师已经处理过，就是一份坏文档。到达关闭步骤的那份摘要，就是组织认为该事故已被处理的那份报告。

把最后一步自动化的压力并非假设。Bridges 等人 [10] 对商用 SOAR 工具做了首次一手研究：24 名参与者、六家产品、超过 200 小时的协同调查。那些工具提升了效率、减少了上下文切换，但也降低了工单的准确性与完整性。让分析师更快地撰写"工单写错无所谓"的自动化，不是一个质量改进——一旦工单被允许自行关闭，那就是一个完整性失效。Islam、Babar 与 Nepal 对安全编排的调研 [26] 已经指出 playbook 语义被当作 ground truth。一个不受信任的规划器——playbook 编译器、检索上下文、任何撰写步骤的组件——提出该步，**提出该步的组件不是验证它的组件**。

公共事故复盘表明：在完全没有攻击者时也会出现失效模式。2017 年 Amazon S3 事故：一名授权工程师按既定 playbook 输错了一个输入，移除了远超 playbook 意图的容量 [3]；执行的写入偏离了批准的内容，而写路径上没有任何东西能挡住它。2021 年 Facebook 外网事故：一条例行维护命令因为本应阻止它的审计工具崩溃而关停了全球骨干 [28]。2024 年 CrowdStrike 事故：一个验证性 bug 让数亿台设备陷入停机 [13]。这些事件中都没有恶意提案者；每一个都是一次缺乏提案者未曾撰写的可靠重建的处置写。公共领域里确实存在对 SOC 处置的攻击字段，我们不假装不存在；但复盘之所以精确指向这些，正是我们把评测构建为边界注入、而非等待一份无法共享的语料的原因。

本文两侧都不依靠某种现成的良好实践。自动化编排工作评估的是流水线质量：SOAR 平台上的自动化会自动处置，但把 playbook 语义当作真理——如果 playbook 说 containment 步是 ran 且工单可以 close，它就 close。两者都没有提供关于 close 与 dispatch 的证据，而这些证据是规划者并未撰写的。

本文把一种性质命名为**事务证据完整性（Transactional Evidence Integrity, TEI）**，并在两条写路径上实例化它。我们不声称一个保护域：一个能窃取处置登录或 kube-admin token 的主机在我们的模型之外，我们也不称其为检索监视器（第 4 节）。我们声称的是：一个持有主规划者特权的提案者无法签发最后一次写，且该谓词是在与该提案者撰写的非规划者事实的同一事务或准入评审中重建的。图 1 把 SOC 构建放在产品写路径上；图 2 展示攻击者可以撰写、但谓词无法表达什么。

**贡献（Contributions）**

- **C1（引理 1）**：请求可见的函数 AttView 没有实现 TEI(ii)。Clark-Wilson 的 IVP 假设一个存储视图；用 π ∈ II（OPA、Gatekeeper、HMAC 属性、附加拷贝）填满它，都不能决定 close 或 bind。引理是关于视图的接口事实，不是一条新的完整性公理。SOC 测量是该不完备性的 OPA 残差 16/45 与 HMAC signed_attribute 残差（同一文档，16 个案例）。kind 属性臂上的二次测量：CONTINUITY 介导认证上下文组件；签名属性仍满足引理的前提。
- **C2（SOC 构建）**：四条证据谓词加一条 PostgreSQL 角色拆分，构建了对工单上 TEI 的反驳。证据谓词：close、bind、verify、egress（§5、§8）。
- **C3（边界注入；危害来自世界状态）**：我们在一个作者自建套件的系统边界处注入，并从存储事实打分，而非从中介器返回值打分。该方法暴露了两条谓词级测试完全看不见的 fail-open 路径（§9.10）。语言模型规划者——四个模型家族各五个臂——是一个存在性检查：规划者可以是模型，而不是模型评测。
- **C4（可检查规约）**：一个 TLA+ 模块 TEI.java TLA 检查一个有限片：tei.cfg（无 CE，10800 不同状态）；两个检查器门：tei-attribute-only.cfg（close/bind CEs）、tei-view-pair.cfg（InvViewClose CE）。tei-minus-cas.cfg（InvCAS CE）。tei-reads-s.cfg 是 Attribute-Only 的对偶：评审者只读 S 而不变量保留。人工构件是 next 下的有限片。Claim-CAS 是状态层引理（§7）。
- **C5（kind 实例化；危害来自世界状态）**：我们的对象模型上的同名义务——Gatekeeper（仅请求对象）对比验证性 webhook，后者重新 GETs Approval、重新哈希 spec、并从 kubectl get（应用后）隔离就绪性、检查身份是否来自注册中心。危害从 kubectl get 后评分，而非从准入 HTTP 返回值。表不与 57 合并。这不是生产集群，也不是云厂商平面。夹具 22/22（A0–A5 映射）在 CI 中驻留两个生产原生准入；CI 不带 kind 失败，也不是 headline。kind 表是从 kind 的 kubectl get 打分（kind_cluster，Gatekeeper v3.17.1）。一次托管两节点 ACK 运行（§9.1）。
- **C6（可移植性；第三个引擎）**：本文中的写路径上的四个义务与引擎无关：Temporal 更新处理器在持久化工作流状态上事务性地评估谓词。七种映射攻击案例：朴素 7/7、请求-属性 6/7、TEI 0/7；金闭包在每个臂下完成（§9.2）。

**非声称（Non-claims）**。我们不声称一个保护域、一个新加密原语、一次检索或多智能体贡献，也不声称对 jailbreak 的防御。我们不把 administrator force_close 当作一种 close。我们不把 mock 适配器的确认当作真实厂商确认。我们不在 harm 本来就不可达的情况下声称 harm 被阻止（§9.9）。我们不声称新的完整性公理、外部威胁语料库，或映射的 CVE 在原始产品上被复现。Java TLC 在有限片上不是实现的证明。

## 2 系统与威胁模型

### 2.1 流水线（Pipeline）

告警从厂商产品摄入为一个事件。一个不受信任的规划者提出动作。可自动批准之上的动作需要一次记录的人类决策。批准的动作被认领和执行，要么通过受管厂商适配器，要么通过直接工具。一个验证阶段观察效应是否发生。一个终端写回被写入厂商侧，通过一个发件箱。只有在那之后事件才到达 CLOSED。图 1 是一条流水线画成，箭头到达厂商或只有 CLOSED 被中介器标记。

外部世界由厂商上的实体状态和我们这一侧的关闭记录组成。这三者不可互换。一个主机可以在工单保持打开时被隔离；工单可以在厂商对象未被触碰时 close；终端处置到达厂商的写回可能来自错误的对象。中介器存在，是因为允许规划者声明这三者中的任何一个，最终都会失败。

规划器被允许在计划内容中写：工具名、目标、参数、指纹 label、playbook 引用。它不允许写的是状态列、批准记录、发件箱投递状态或事件的处置来源——操作者选择的定位符 outbound guard 用作对象身份的见证者。这种拆分是数据平面假设，评测中的每次注入都尊重它。

### 2.2 攻击者（Adversary）

攻击者在数据平面。它编写：工具名、目标、参数、级别、执行者、源定位符、指纹 label、模板名、playbook 引用。它提供工具和适配器返回的内容，包括声称成功的回执（模拟的）、只有一个确认的回执（模拟的）、以及回显请求的答案（模拟的）。它可以使请求重试并使调度者在人类决策前改写计划。当规划者是一个语言模型时，同一个攻击者也会写入上游自由文本——一个 compromised 的证据或分诊阶段——那就在提示词里；A4 案例（§9.12）就是那样挂载的，且这是不通过 harness 本身注入的唯一注入。间接提示注入 [22, 59] 在此范围内：上游文本由模型撰写，超出作为模型属性。

它不是一次代码执行：它不在中介器内部运行、不在服务进程中设置环境变量、也不写状态列或批准记录——把动作移到 APPROVED 状态、不再回退到任何方案。我们把这些列为已排除，因为它们是使评测可解释的因素，而不是因为它们舒适。图 2 是一个拆分，这样论文的其余部分可以指出它在哪里，而不是重述它。

该模型更接近 Clark 与 Wilson 的良构事务 [12]、Biba 意义上的安全晶格 [8, 17]，而不是 Hardy 的混淆代理 [23] 意义上的 sandbox 逃逸故事。规划者被要求组织一个它无法保证的登录上的授权。中介器是认证结果状态的完整性验证过程，而非该状态本身的声明者——假定存储是真实的，它们在 Anderson 意义上 [5] 是一个 IVP 与一个属性-唯一策略。我们在第 4 节拒绝防篡改，但在声称任何其他东西之前，确实在那个地址空间里：规划者登录无法写入阴影列。Lampson 的观察是：保护是主从与客体 [30] 之间的一种关系；我们的 outbound guard 的见证，是事件的操作者选择的处置来源，而非命令本身携带的定位符。

## 3 事务证据完整性（Transactional Evidence Integrity）

**定义 3.1（TEI）**：一次处置写（工单关闭、厂商分发或外包集群变更）被中介化，当且仅当 (i) 最后一次写是规划者登录无法签发的特权；(ii) 谓词在同一事务或准入评审中重建，从规划者无法读取的持久事实（发件箱游标、重计算指纹、ingest 拥有的定位符、ingest 持久化的批准、隔离状态的持久化重读）；(iii) 观察路径对规划者无突变。

四个 SOC 中介器是工单上 TEI 的一个构建物，而非其性质。表 3 是字面的对象映射：请求体自报（规划者写的指纹列、metadata.name、webhook encode 的协调条件）不是见证。属性形态准入可以拒绝格式不良的请求，但不能拒绝一个格式良好、其理由仅是一份回执、而该回执本应派生自写操作的请求。

**引理 1（请求视图函数不能实现 TEI(ii)）**。令 AttView 为请求可见投影（callerCycle、plannerFp、signedOk、attachedApprovalCopy、reportedReceipt 等）。令 II 为该文档中所有 AttView 函数的集合。设 CloseOK 保持重建存储循环等于调用者循环。存在可达状态 s 与 s' 使 AttView(s) = AttView(s') 而 CloseOK(s) ≠ CloseOK(s')。因此 π ∈ II 不能实现 TEI(ii)。

OPA/Gatekeeper/CEL 之上：HMAC signed_attribute，一个同时查看请求的谓词；不在侧边栏或已批准拷贝上执行 GET；SQL join 针对周期/批准/发件箱；观察重读隔离状态；在持久的批准内容同一事务中重计算指纹。这些读是 TEI，而非该引理的反例。

双规范 TEIPair 检查 AttView(A) ⇒ CloseOK(B) = CloseOK(B)。Java TLC 在 HonestAdvance 与 PlannerStaleCycle 上违反它（§7）。AttributeOnly 是一个 π ∈ II 的闭包测试，只看自一致性，TLC 找到 PlannerStaleCycle→CloseAccepted 与 PlannerForgedFingerprint→DispatchAccepted。InvEgress 仍持有，与 OPA 侧 A4 覆盖匹配。SOC 16/45 残差（§9.1）是在两条写路径上测量 II 的两个构建物，而非产品排名，也不是引理的证明。

Clark 与 Wilson 的 IVP 假设读取一致数据项。用 π ∈ II 填满它就是上面定义 3.2 的不完备性。TEI(ii) 的要求是 IVP 在同一事务或准入评审中读取存储。四个 SOC 谓词与关键 webhook 是该接口的构建物（表 2）。

设 S_close = {rebuildCycle}，S_bind = {recomputedFp}，S_egress = {eventSourceOnly}，S_verify = {observedIsolate}。评审实现 CloseOK 当且仅当它在同一事务或准入评审中读取 S_close；绑定、外发、验证分别读取 S（上述）。一个接口完整性检查——谓词集合形状——是对 close 的新不变量，而非新公理。tei-reads-s.cfg 在 CE 上如此。

表 3 是文献锚定分类，而非搜索词。工件中的协议（eval/taxonomy/sampling.md）列出了固定查询和包含/排除 rubric。该协议中的已引论文是相关工作：已实例化的是已映射到我们对象模型的工作——它们不是原始产品上的复现。可映射项落在 T1–T8 上；新类需要 T9 对象 + 危害谓词。该切分并不强制 T9 分布；那不是开放世界分布的抽样。

## 4 可信计算基（Trusted Computing Base）

我们在讨论系统前先声明边界。图 2 是攻击者视角的同一条线；本节命名受信侧的模块。

**边界之外**：规划者输出与提示、检索上下文、工具返回值与执行器回显、报告体与决策轨迹、orchestrator 检查点自报、面向厂商的 UI 拷贝，以及任何接收字段——无论是厂商 stub 还是真实厂商提供。这些都不是中介器的输入（中介器相信的意义上）。回执被分类而非相信；指纹标签的规划者写被当作不受信并被重算。

**边界之内**：发件箱 worker——处置数据库行，是唯一可以写 CLOSED 或插入发件箱行的角色；PostgreSQL GRANT 使那将一个特权角色而非函数；终端动作上的数据库约束与动作声称；批准记录——其批准记录上的指纹被从当前内容而非规划者写的列重算；部署这些约束与角色的迁移；运维默认是两个 OS 进程和一个 PROC_ROLE=actuation 的 API 与调查 worker。我们将其拆分以测量：规划者子进程不能构造工厂，规划者 SQL 被拒绝（SQLSTATE 42501），处置父进程仍能 close。评测矩阵写规划者行和 A0 语句，这些规划者子进程；父进程持有登录，因为它是允许 close 的进程。Redis 是缓存和预算计数器，不是处置真理的来源；中介器必须在重启后正确读取数据库。

**受信但未中介化**：主机和处置凭证。中介器仍然是进程可以调用的，而非受信保护域。一个能执行 root 代码的攻击者、或窃取处置登录（我们的模型中在我们之外），这就是我们拒绝 Anderson 防篡改声明而做角色拆分的原因，也是为什么我们不称之为结果监视器。角色拆分所改变的是规划者：一个只持有规划者登录的进程，即使 raw SQL 也无法写两个特权列，A0 测量这一点，因为这是一个数据库事实而非门。Rushby 对 TCB 的定义 [41] 是：策略成立所必须正确的东西很短：如果处置角色是 CLOSED 和发件箱的唯一写者，且 compromised 规划者登录不能改变世界，那么评测配置在 §6.2 中描述的两个 OS 进程中切换，并为套件消除这两个中介器；消融它们不属于生产边界，也不出现在图 3 的产品路径中，它们不作为可变环境中的部署，也不削弱那个使它们编译出来的较弱边界，我们不声称更强版本。

**受信但不属于我们中介化的部分**：适配器忠实报告厂商侧的内容，这就是为什么回执被分类而非相信，以及操作者对事件处置来源的选择是 outbound guard 用作对象身份的见证。一个说谎的 vendor 在我们工作范围内；一个谎称收到确认的 compromised 适配器也在范围内。

## 5 设计（Design）

每个中介器以相同方式呈现：它回答哪个攻击、检查什么、错误码，以及评测在移除它时观察到什么。

我们的比较器之所以是四个函数而非一个策略，是有原因的（§9.7 后置）。单个准入检查越出外发信封，就可以拒绝一个合法命令，且可以拒绝彼此不一致的合法命令。它不能拒绝一份理由是回执的畸形命令；它被告知所有内容，一个批准必须在同一事务中重读，一个观察永远不会产生效应。三者同时为真，调用者持有表。把检查放在事务中、事实为真的那一刻，就是设计的目的：拆成四个站点，每个事实只在它为真的地方使用。本节其余部分按此逐站点处理。

### 5.1 关闭需要收敛证据

**攻击**：规划者以自己的叙述为基础，得出事件已处理并驱动事件到 CLOSED，一个从未确认的回执、模拟的厂商 stub。
**检查**：每一个进入 CLOSED 的普通转换都被中介化。状态机从数据库重建关闭上下文，而非从调用者论点。一个在 handler 中有良构上下文的规划者仍需满足当前行谓词。一个未知名位置默认为默认。当策略要求时，关闭还需要报告、适用副作用已收敛、所有终端处置状态同意，一个 CONFIRMED 回执绑定到当前计划版本和关闭周期。一个 CONFIRMED 回执，在非模拟处置路径——{readback_verified, manual_confirmed} 中——就是。代表代码是 closed_requires_report、closed_side_effects_pending、closed_weak_confirmation_evidence 以及 closed_simulated_receipt_rejected。

最后一个连词要求终端写回行，不是它的投递、也不是厂商回执。它不能要求回执，因为关闭是使头部可投递的转换；要求回执会让回执变成循环。不变量 4 明确陈述了这一边界。什么阻止永久本地/远程分歧是发件箱，不是门：头部是有界的，工作重试，不能投递到死信的头部保持可见。

**评测观察**：卸载该中介器恢复 A1。§9 的留一是 +17 harms，最大的单一中介器裕度，这正是预期形状：套件试图从不完全证据中关闭工单。

### 5.2 分发必须匹配已批准内容

**攻击**：人类批准一个地址；计划随后被修订，使分发动作携带不同的目标、不同参数、更高特权工具或更低级别，而存储的指纹标签被重写为匹配。
**检查**：批准记录存储一个在分发内容（事件、计划版本、工具、目标类型与规范目标、归一化参数、执行者、批准模板与 playbook 绑定，附录 A）上重计算的指纹。认领动作时，监控从动作行重算该指纹、读取认领所在的行、并比较。一次第二次检查发生在投递前，当动作自上次认领以来已被撤销或取代。将动作的存储指纹列与批准记录的同一列比较——因为规划者写该列：这是两条 fail-open 路径的第一条。代码：action_content_drift、plan_revision_mismatch、playbook_binding_mismatch。

该指纹是内容寻址承诺，Merkle 意义上 [32]；批准绑定到将要分发的内容的摘要，不是到一个工作流步骤标识。SOAR 平台典型地批准一个工作流中的步骤 [37]；一个不受信规划者可以重写该步骤的 payload 在事实之后，该事实使写入的对象变成错误对象。

**评测观察**：卸载该中介器恢复 A2。它也恢复 A4 案例中的定位符交换，因为处置来源定位符也是十一指纹片段之一，在批准后移动它也是内容漂移，因此这是一个外对象写。

### 5.3 观察效应不能凭空产生一个

**攻击**：规划者报告 containment 已被验证，要么通过回显请求作为观察、要么通过激活验证阶段本身的终端写回。
**检查**：Phase 1 观察已执行且未激活终端写回；延迟后验证动作被跳过、未失败。一个说 SUCCESS 但没有 _is_verified 的工具结果是不可验证的。一个 _need_replan_ 或 _need_manual_ 的 Phase 1 结果不能变为激活。该拆分是准备好承诺 [21] 应用到一个不被信任报告自身状态的规划者："prepared" 是一个待验证的声明，不是协议消息。

**评测观察**：卸载该中介器恢复 A5。在更早的修订中，它还隐藏了 full 下没有 split 的情况——一个延迟验证算作失败，动作从未关闭，且弱回执从未发生。那个洞已在 §9.9 关闭，教训是：一个中介器可以通过中止工作流来掩盖另一个中介器的失败，而我们报告单元而非单个聚合。§9.5 的开销几乎完全是这种拆分的额外一次往返。

### 5.4 分析内容不得离开

**攻击**：报告体、提示或决策轨迹随厂商处置载荷骑出，要么通过额外键、要么通过在另一个对象重新定位命令。
**检查**：外发处置命令必须在每意图字段允许列表内（14 个字段，生产信封而非猜测集），必须不携带任何分析或安全形状内容，且必须命名其事件操作者选择的处置源名。扫描中的内部失败会拒绝命令。允许列表是完整中介外发 [43]，定位符检查是混淆代理修复 [23]。代码：no_analysis_content、disposition_field_allowlist、disposition_source_match、outbound_guard_internal_error。

§9.10 的第二条 fail-open 路径就在这里：locator 检查的第一版将命令自身的源定位符与其自身作比较。从事件创建源获取见证是第二个错误，因为合规命令合法命名创建该事件的对象。操作者选择的处置来源才是被允许标识对象的那个。

**评测观察**：卸载该中介器恢复 A4。三个可切换中介器在数十微秒内决定。这是它们中的一个。检查成本不是部署会留着它的原因。

## 6 实现（Implementation）

原型是在 PostgreSQL 16 与 Redis 之上、FastAPI 服务，使用 SQLAlchemy 2 异步会话、Alembic 管理的 schema、以及一个排空发件箱的 Celery worker。四个中介器是该路径上的普通函数，不是侧边栏。发件箱是事务发件箱模式：命令在同一数据库事务中插入到证明它的状态行，worker 稍后投递，因此 "决定写回" 与 "厂商收到硬件" 之间不会有崩溃。终端头部的血缘是 Saga [18] 而非分布式事务：每个新头部使前一个退役，补偿本身就是一条发件箱命令，没有与厂商的两阶段提交。

### 6.1 可切换层之下的中介器

双重调度不由四个门中的任何一个中介化。它由四个部署不能关闭的机制中介化，并因此分别评测：部分唯一索引，每个活动头部最多一个终端头部（按事件、关闭周期）；在投递时继承先前头部的行内事务；比较并设置的动作状态写入，使第二个 worker 找不到可认领；比较并设置的 claim 头；以及每个槽一个规划者的单一活动头，这是单头部不变量的实例化。字段级写权限和单执行器所有者是该类中的安全属性。

若这些开关中的一个会削弱我们测量它的能力，则危害会削弱底物（§9.4）：从评测数据库移除索引并替换朴素形状的每个代码级机制。生产代码不变，且不包含禁用它们的路径。

### 6.2 评测开关

原型读取四个设置，每个禁用一个中介器，每个门（EVAL_DISABLED_ 后跟 CLOSED_GATE、FINGERPRINT_RECHECK、VERIFY_PHASE_SPLIT、OUTBOUND_GUARD）。它们存在是为了消融能从真实链中移除一个中介器，而非测试一条不同代码路径。四者默认加载中介器，且任何一个被禁用时都会构建一个 harness 拒绝的构建。设置它们中的任何一个都不能卸载一个中介器：一个每次启动失败的进程，是对操作员错误的守卫和防篡改论证，环境变量不被边界 §4 卸载中介器。

评测 harness 生活在单独的包中，生产代码不导入它。它构造同一服务图，用记录适配器替代厂商适配器，并使用可选观察表面。它从数据库与厂商侧事实打分。底物削弱——丢弃部分唯一索引、替换锁竞争、无操作取代、总是 true 投递断言——在生产代码中找不到该字符串。想要知道生产能否被拉进关于 claim 的论证的审稿人：字符串不在那里。

### 6.3 部署实际运行什么

一个生产部署是两个 OS 进程。规划者进程（API 与调查 worker）从四个中介器加载、部分唯一索引和迁移安装的两个数据库角色开始，规划者数据源名，且无动作数据源 URL——该进程中的处置 URL 是 fail-closed 违规。处置 worker 持有写登录，是唯一处理事件、排空发件箱或 force_close 的进程。缺失 DSN 要求进程拒绝启动，且无环境变量能卸载中介器。关闭与外发入队使用活动登录；规划者登录不能签发那些语句。actuation_writer 不是 ALL TABLES：它可以 SELECT 广泛、且只向特权路径（事件状态、发件箱、回执、执行作业投影、源序列、上下文闲聊、审计行）写入。发件箱 worker 是唯一调用厂商适配器的进程。人类批准是一份带重算指纹的记录决策，不是一个翻转布尔。force_close 存在、被角色检查、设置 external_unsynced、从每次关闭计数中排除。关闭计数是我们报告的。该系统是读者可以部署的系统，我们正在评测它，且切换和底物削弱是测量仪器。

四个检查是普通函数，不在路径上、不是侧边栏、不是内核。Close 是状态机中的 validate_closed_ 门，在每个进入 CLOSED 的普通转换上调用。Bind 是认领时的播放，在同一行状态比较并设置中。Phase split 是验证-1 观察者拒绝激活来自 phase-1 观察的终端写回。Egress 是 on_enqueue 的 OutboundDispositionGuard。想知道给定决策是否正确的审稿人可以在这些名字处开始，§7 的不变量是每个应保持的含义。

## 7 不变量（Invariants）

§8 中的论证按叙述走写路径。本节说路径应保证什么。每个不变量是跨持久状态的谓词，读者可以检查它，而不是相信段落。每个不变量与维护它的代码配对，与观察它的消融配对。配对即要点。一个无消融的不变量只是一句话，一个无不变量的消融只是数字表。

**定义 7.1（处置状态）**：一个事件携带一个计划版本 r(e) 和一个关闭周期 c(e)。一个动作 a 携带一个状态、一个执行阶段、一个计划版本 r(a)、最多一个批准记录 α(a)，以及附录 A 的十一段分发指纹 φ(a)。一个终端头部是一个发件箱行，其 intent_event_update 槽为 σ(h) = (e, c, intent, 逻辑槽)，其血缘指针 s(h) 在 h 活动时为空。外部效应是完成调用厂商适配器提交入口的调用。

**不变量 1（外发完全中介化）**：每个外部效应命令 κ 在同一事务中由一个外发守卫决定，该守卫承认一个载荷，其 SHA-256 等于存储在 κ 的发件箱行上的 SHA-256。

机制：适配器的提交入口有一个调用者，在发件箱 worker 的投递例程中，guard 在命令入队时和分发事务内部再次运行，载荷摘要按写入的方式入队和重算。证据：这是结构性的。消融不能直接测试它：卸载守卫移除检查，不为第二个 claim 留出空间。什么显示守卫有用，是它的反事实——卸载它，A4 就出现在 §9 的评分中，且为零加载。单站点 half rests 检查靠在 inspection 上，我们更愿意将其作为测量来呈现。

**不变量 2（批准绑定）**：如果一个外部效应可归因于动作 a，则在它被认领的时刻，α(a) 存在、处于已批准状态、已提交给确切的指纹 φ(a)、且 r(a) = r(e)。

机制：绑定复核在认领事务内运行，行级锁使 claim 的条件更新生效，比较与状态转换之间无窗口。第二次检查在投递前，当命令已被撤销或取代。证据：A2，朴素配置承认漂移，而中介化的不承认。

**不变量 3（单活动头部）**：对每个槽 σ，最多一个终端头部 h，使 σ(h) = σ 且 sup(h) 为 null。

机制：三层，按其作用顺序：入队事务在插入新头部时退役旧的；部分唯一索引使一个槽只能有两个血缘指针，从不允许两个；投递重读活动头部，如果它不再是最新则拒绝发送。证据：底物消融（§9.4）、多进程探测（§9.6），以及下方的模型检查——这是三个中唯一一个谈论 harness 未产生的交错。

**不变量 4（关闭证据）**：事件到达 CLOSED 当且仅当在转换时刻且从数据库（而非调用者论点）重读时，报告行存在；处置政策已解决；侧效应收敛已存在且已收敛；所有适用的要求写回动作处于已关闭状态；且一个终端写回行存在，其计划修订和关闭周期均与 r(e) 和 c(e) 一致。

机制：一个谓词，在状态机从数据库重建关闭时评估，在唯一非管理边缘上进入 CLOSED。证据：A1。边界：最后一个连词要求终端写回行，不是其投递，也不是厂商回执。它不能要求回执，因为关闭是首先使头部可投递的转换；要求回执会让回执变成循环。因此不变量 4 比"闭包暗含的厂商同意"弱，一个事件可以在写回仍在队列时本地 CLOSED。规则那不让规则不兼容：头部持久、worker 重试、不能投递的头部落在死信中，在可见时而非静默丢弃。我们陈述这一点，是因为读者会假设更强版本。

两个性质从不变量连同 claim 协议中得出，两者都可观察，且评测对它们打分：(5) 一个已批准动作产生至多一个外部效应；(6) 一个被取代的头部从未被投递。

**不变量 5（每动作单效应）**：对每个动作 a，最多一个外部效应可归因于 a。
**不变量 6（无陈旧投递）**：没有头部在它不是其槽的最新活动头部时被提交给厂商。

### 7.1 头部不变量的模型检查

底物消融和多进程探测都回答"这会发生吗"。两者都不能回答"会不会发生"，因为两者都对交错进行采样：消融驱动案例是顺序的，多进程探测通过五轮运行交错 harness 未产生的内容。头部协议协议足够小，因此我们枚举来回答第二个问题。

我们将 claim、enqueue 与交付转换为迁移系统，并进行广度优先探索可达状态空间，为每个不变量寻找最短反例。模型编写时绕开了真实协议中笨拙的部分：入队头部在它插入的活动头部上持有行锁，两个这样的入队使先前头部被序列化，两个使 none 成立；该锁上不等待者在授权时不重新扫描，因为 PostgreSQL 重新检查锁上的谓词并在谓词不保持时删除行而不重新执行查询；取代和插入是一个事务，因此唯一违例用 supersedes 携带它回滚；投递事务在其自身头部上跨适配器调用持有行锁，携带血缘指针的头部被无条件拒绝，这不是四个可切换机制之一。

两个场景重要，顺序状态对构成。在共享动作下，K 个 worker 竞争执行一个已批准动作。在不同动作下，每个 worker 持有其自己的已批准动作——一个修订后的计划，或同一槽的二次关闭尝试——每个 claim 合法成功。表 5 报告三件值得分开的事。

首先，部署配置对每个交错保持所有四个不变量，K=2,3,4；K=4 与多进程探测宽度相同，因此该宽度中探测的零不再是样本。

其次，两层不是冗余的：它们覆盖不同竞争。在共享动作竞争中，头部机制两者都不在决定：claim compare-and-set 允许一个入队者，因此状态空间是 225 状态宽，且与索引是否存在无关。在不同动作下竞争，compare-and-set 不决定任何事，因为两个 claim 都是合法的，索引变成两个已批准终端动作和两个活写回之间唯一的事物。一个倾向于称所有这些为 belt-and-braces 的审稿人应该读表的两半，而不是答案。

第三——这是我们没预期到的发现——丢弃三个机制中的**任何一个**都违反不变量 3：

(1) w0 以 compare-and-set 认领动作 0，成功。
(2) w0 SELECT 先前头部 FOR UPDATE；不返回任何内容。
(3) w1 以 compare-and-set 认领动作 1，成功。
(4) w1 SELECT 先前头部 FOR UPDATE；不返回任何内容。
(5) w0 插入头部 0。
(6) w1 插入头部 1。

行锁不能序列化两个不命中锁的入队，因为 in-transaction supersede 无事可做，索引是唯一的剩余检查。顺序底物消融为该 arm 记录无变化（§9.4），它准确预测了它测量到的：第一次入队使头部成为最新，第二次总是看到最新，因此单独的 supersede 就足够。该 arm 看似冗余，因为 harness 无法产生使它 load-bearing 的交错。再走两步，同一消融交付一个不再是最新的头部，因为投递时机重读并发现一个更新的活动头部，而非已取代自己的头部，且血缘检查本来会 trip——这正是 supersede 从未有理由写入的指针上的检查。

## 8 安全论证（Security Argument）

论证是一条路径，而非证明：对每个外部效应，我们枚举从不信任提案到该效应的边，并命名最后一条边的唯一写者。图 3 是同一论证的图片，且不包含评测开关。

**到达厂商**。厂商状态只通过处置命令改变，且系统中每个命令在单个调用点提交到发件箱 worker 的投递例程。命令进入发件队列，outbound guard 运行，且投递重新断言头部即将发送，仍是该事件（事件、关闭周期）的活动一个。命令的内容是该行动已被认领的。认领是在绑定复核也运行的行锁下的一个单条件状态更新。因此边链：提案 → 已批准动作行 → claim（绑定）→ 入队（guard）→ 投递（活动头部）→ 厂商。想要对厂商有不同效果的规划者必须越过 claim 和队列，因为适配器没有其他调用者，且规划者登录不能插入 worker 将投递的发件箱行。

**到达 CLOSED**。代码库中两个例程写事件到 CLOSED，且都作为处置数据库角色发出更新：进入 CLOSED 的普通转换，通过关闭门针对从数据库重建的上下文验证该边，以及 administrator force_close，它是角色检查、设置 external_unsynced、从威胁模型和我们报告的每个关闭计数中排除的第三例程。发出 UPDATE ... status='closed' 的规划者登录被 PostgreSQL 拒绝（SQLSTATE 42501）。A0 即那个。第三例程可以在软时间限制上写 FAILED，且不能写 CLOSED。Orchestrator 检查点、报告生成和编排服务不写事件状态；它们调用状态机，或写它们经过同一机制的补偿动作。

**到达 "verified"**。验证阶段可以写一个效应状态，不能激活终端写回；激活是一次单独的出阶段 1 结果允许它的激活。因此工具结果不能成为该写回的原因。

**残余信任**。主机和处置凭证。我们对完整的信任：安装部分唯一索引和两个登录的数据库，以及适配地忠实报告厂商侧内容的适配者的忠实，这就是为什么回执被分类而非相信，且操作者选择事件处置来源是 outbound guard 用作对象身份的见证。我们不从这些中声称任何东西。

故障关闭成本，在负载下，是卡住工单，而非 151 ms 验证 hop。金负载下 120 工单固定范围，full 仍关闭 40/120（wall p50 3641 ms、p95 5279 ms、p99 6235 ms），平均 READY depth 为 0；该数字驻留在事故中。属于该句子的测量是混合到达过程：120 个到达、30 个拒绝种子、确定性时钟 Poisson。两臂关闭 80 个金事件。那 40 个拒绝种子在 naive 下 harmed（40/40 closed 错），full 下未 harmed（40/40 打开，无 harm），带工单停留时间 p50 56.8、p95 109.1，该时钟上 READY 发件箱深度为 0。那些拒绝从未成为未投递命令。工单积累在人类需要查看的事故中，这是安全结果的最真实代价。

卡住工单的成本是人类工作量。运行中的每一张工单都经过一个拒绝，并且跨四个：closed_side_effects_pending (17)、closed_weak_confirmation_evidence (12) 和 closed_requires_report (11)。拒绝名称是失败的谓词，且工单保留已评估的证据状态，因此分诊是一个查找——哪个证据项缺失或弱——而非取证重建。比较工单是人类工作又一。红旗工单需要一个人在卡住、手动解析或 blocked 时；在 naive 下，是所有 120 个到达，因为没有 typed 输出的验证无法解决良性，且四十个仍然关闭错误。在 full 下，正是那 40 个类型化工单，良性的一个都不是。清理一个类型化工单需要分析师 8 分钟，批处理成本 40×8 t_h，假设每工单五分钟，约为 120 个到达的 3.3 分析师小时，队列在拒绝前有界。我们将 t_h 作为假设，而非测量。故障关闭做的是在该做时集中少量工作到那些应得的工单上，而不是在每次 arrival 上散布无类型工作。

### 9.7 比较器：同一四个点的外部策略引擎

中介器在系统内，明显的反对是它们不需要成为：标准方式是策略引擎。我们以标准方式将授权放在动作之前，且如果我们能，贡献是部署细节。我们直接测试了它。external_opa 臂卸载所有四个门并咨询一个真实 OPA 服务器 [34]，在同一四个决策点——分发前、观察后、关闭前、每个外发信封——honor 不继续的拒绝。策略是纯 SCQL 文本。

我们以对我们有利的方式进行比较器。OPA 是真实二进制而非我们自己规则的重实现。它在每个决策上同步咨询，无缓存，无故障超时，比侧边栏部署更好。其外发规则逐字段允许列表真实写回信封 schema，而非猜测。且它被给予一个朴素框架本会保留的两个事实：受信源本地目录，调用者通过它传递给 in-system guard，可以通过侧边栏，验证结果自己的细节，告诉读者背后的证据是声明效应成功而非独立读回。 withholding 任一事实会使比较器在每个中介化决策上失败。我们在决策文档中以键值序列化并发送。单个差异账户解释了结果。

### 9.9 naive 配置下不可达的危害

四类单元格在四个中介器下为零，读它们作为中介器将错的证据。

所有四个 A3 案例在门消融的每个配置下都为零，包括 naive，且读到这些为零意味着什么错：四个门中没有一个防止双重调度。防止双重调度的是底物，且 §9.4 的臂测量它。

该列中的两个工具 bug 我们报告，因为两者都产生看起来像结果的零。厂商 stub 最初将投递重试计为第二个外部效应，这使 A3 在 stub 下闪烁，直到我们在其广告的幂等契约上驱动该契约，且效果按例计数。然后两个案例被驱动，驱动该机制从未达到：一个为同一动作的两个激活竞争，应用级预检查首先回答，另一个重放已投递的头部，其中 delivery-status 转换首先竞争。现在两者都在头部之前携带两个已批准终端动作。索引和 supersede 是仅有的东西。零只有在它能产生一个时才是证据，且这两个运行做不到。

一个 A2 案例，批准级别降级，在 naive 下被批准记录上的级别验证检查阻止。该零同样不可切换，但它不被归因于绑定复核。

## 10 讨论（Discussion）

规划者不在边界中，处置逻辑在。我们声称的一切都是关于决策和数据库中发生的记录，不是关于规划者的诚实。一个提出自己不会写坏行的提案的语言模型，既不是响应也不是缺陷。脚本规划者存在，使问题变成"检查是在那里"——这是一个是或否的问题。语言模型臂是检查模型是否能在座位上的存在性。五个 A4 案例以说明性方式：两臂（kimi-k3 两次、claude-opus-5 三次）将注入叙述复制到目标字段，且那些试验每一个在 naive 下打分危害、在 full 下被阻止——中介结果，而非空闲零。没有臂授权注入的凭证；那些零保持空闲，且我们如实报告。将两个规划者合并在一个合并表中会让幸运模型膨胀中介结果。

Mock 确认比 live vendor 读回弱。两个厂商列从不合并。一个早期修订在没有确认字段的 AC 上留下双列关闭作为残差标题；关闭谓词现在在 mock 上与 live 合同上要求相同的强确认（§9.9）。将 mock 适配器确认视为 live 确认的部署对我们测量的东西有较弱主张，我们不声称否则。

UNVERIFIABLE 不是成功。一个说 SUCCESS 但无 _is_verified 的工具结果是不可验证的。将其折叠为观察使该效应。阶段拆分保持两者分开；开销在 §9.5 是查找的成本。

单适配器不泛化到任何 vendor APL。记录供应商合同：submit、confirm-readback、idempotency。其 API 无法表达确认读回的厂商不能满足关闭门，且不能投资，我们不与真实第三方厂商评测。envelope_b（§9.11）是我们控制中的第二个存根，我们不声称信封映射到部署产品。

Administrator force_close 是一个声明的旁路。它被角色检查，标记事件 external_unsynced，且从每个关闭计数中排除。想要它作为中介化关闭的读者被警告；论文不排除它。威胁模型是数据平面，且具有该角色的管理员不在其上。

完全中介化，而非参考监视器。Anderson 的参考模型声明是防篡改、总是调用、小到足以验证 [5]。我们声称后两个，理由是面向终端命令的两方面（不变量 1），且明确首先不声称第一个。角色拆分使最后写成为特权，而非功能约定；它仍不是保护域。Saltzer、Reed 和 Clark 的端到端论证 [42] 是关闭门从数据库重建其上下文而非信任上下文对象已经持有该属性的理由。Schneider 的可执行安全策略 [45] 边界是运行时监视器能保证的；我们通过将 claim 限制在我们实际拦截的写路径前缀上来保持在内部。

我们希望读者带走的：那四个 Python 函数是 SOC 安全的。AgentDojo 上得分良好的模型因此与发件箱有连接。该唯一索引是可选的，因为存在表 5，且 151 ms 是为什么不是。开销是"151 ms，而不注意时一轮三轮，四个检查中三个是免费的"。

本文未测量的：57 个案例是作者构建的边界注入。覆盖搜索枚举完整实现旋钮空间（960/960 点；六个覆盖单元格；full 下无新危害类），不是开放威胁分布。A3 在 naive 下为 0/4 是底物，不是四个门。五个模型家族模型在规划者座位上作为存在性检查，N=5 每，且无字段 SOC 跟踪。Mixed-load 后备 120 到达，40 拒绝和 40 停滞（full 下）：故障关闭有队列成本，不是效用缺失。第二个厂商信封（envelope_b）单独报告（§9.11）且从不合并。Kubernetes 实例是一个 lab kind 集群加一个托管两节点 ACK 复制。两个是五个模型臂的：将注入叙述复制到目标字段的两个臂，将 A4 案例变为中介结果（3/25 跨臂、blocked under full），无臂授权注入凭证（0/24 scored），因此那些保持空闲且如此报告。一个其 API 无法表达确认读回的厂商不能满足关闭门，且诚实行为是拒绝关闭。仅规划者进程拒绝失败工厂；公平部署是拆分。那些都不是扣留结果的理由；它是理由而非拆分，因为它是表。

生成式 AI 署名：语言模型臂在规划者座位上作为实验对象，而非作者。如果本手稿中的任何散文用生成式工具进行了 copy-edit，相机证据将根据 ACM 出版物作者政策声明；评估数字不是这种使用。

## 11 相关工作（Related Work）

下面每个组是可能合理吸收这项工作的邻域，因此每段以它声称为什么不这样做结尾。

**中介与完整性模型**。完全中介化、失败安全默认值和经济机制是 Anderson [5] 与 Saltzer 与 Schroeder [5, 43] 的；这些原则谈论的对象和原则是 Lampson [30]。问题的形状——一个在别人的权威上操作的组件无法对输入说不——是 Hardy 的混淆代理 [23]。Clark 与 Wilson [12] 比 Biba [8] 的完整性晶格或 Denning 保密性晶格 [17] 更接近我们的设置；它们的完整性策略基于良构事务和完整性验证过程，后者比产生它的程序更信任。那个 IVP 假设读取一致数据项。将其部署为 π ∈ II——OPA、Gatekeeper、HMAC 上的请求属性，包括附加批准拷贝——是不完备性，引理 1 陈述。TEI(ii) 是 IVP 在同一事务或准入评审中读取存储的要求；四个 SOC 谓词和 kind webhook 是该接口的构建物，而非新公理。调度时的复核是一条时间到时间使用论证 [9] 关于一个批准而非文件句柄。差异：我们不提出新完整性公理。我们记录接口事实：一个 IVP 填满 π ∈ II 不能决定 close/bind，且我们构建一个读取存储的。我们仍不提出保护域（§4）。

**参考监视器实现与更改绑定**。Flask [47] 和 SELinux [31] 是 Anderson 三要求在一个内核中的经典实现。Cerglegoglu、Galletta、Degano 与 Basin [1] 测量信息流规范在 SELinux 中表达了多少；我们测量工作流中 IVP 是如何在签名请求上表达的，且我们不实现一个 IFC 类型系统。变更启用 [2] 是操作实践，将更改咨询建议绑定到变更请求；差异：我们拒绝防篡改声明，那些内核监视器存在，且我们不是 SELinux 的策略语言。我们从该线取的问题——TOPS 已经问过的——是最后一次写是否是中介特权，以及它是工单关闭还是厂商分发。ITIL 邻域将人类决策绑定到工单变更；我们的绑定复核检查那些将实际分发到事件内容的元素，且 A2 是两个在生产 bug 上相遇的地方。

**控制平面准入**。Kubernetes 准入控制器 [51]、Open Policy Agent 与 Gatekeeper [33, 35] 以及 IAM 条件键 [4] 已拦截每个变更请求并对照策略评估。架构上，四个中介器。差异：那些系统对请求施加 schema，而我们的世界案例在格式不良请求上成功；它们是良构请求，其理由是回执、先前人类决策或观察——必须从非规划者状态派生的对象——而属性形状准入策略无法表达。

**认证安全上下文组件**。CONTINUITY [arXiv:2609.05269] 是最近的邻域：签名根授权、轮状转换回执、故障注入套件，它在其完整配置下对零有害外部效应进行零。差异：CONTINUITY 介导那些组件上的认证安全，我们跨 vendor 和数据库介导事务证据。签名请求属性仍满足引理 1 的前提；signed_attribute 残差是 OPA 相同的 16 个案例。侧边栏测量缺口：这些需要请求内部或关闭事务的事实。

**数据库特权、能力与处置中的动作**。PostgreSQL column GRANT 和行级安全是使最后一次写成为特权而非如果 [52] 的经典方式；Hardy 的混淆代理 [23] 是为什么我们将该计划当作不得继承处置登录的代理。工业控制和 OT 完整性工作将处置视为命令式状态变更到 plant state [48]；最近 TOPS 信息流策略测量 [11] 与准入控制线已沿此线 [35, 51]，是我们所站的邻域。我们表明此路径上的最后一次写是数据库特权，且四个证据谓词加该特权是侧边栏无法阻止的损害原因。

**工具使用 agent 的可信计算基**。CaMeL [15] 在特权和量化模型之间放置能力追踪解释器。IsolateGPT（也发布为 SecGPT）[57] 隔离第三方 agent 应用彼此。Wu、Cecchetti 与 Xiao 的 f-secure LLM 系统 [56] 将规划器与可执行策略执行分离，两者都使不受信输出远离规划。双 LLM 模式 [55] 和指令层次 [53] 保持受信输出在控制流外。AgentDojo [16] 在提示注入下评估这些防御。差异：在轴上，我们是在信息和控制流内进行中介，而你所站的是更强的——我们不对提示注入提出主张，问题是外部 agent 的提案可以任意被破坏，且事件记录是否可以关闭。数据流向不回答其中任何一个，因为证据驻留在厂商和数据库中，而非 agent 变量中。

**Agent 安全基准与工具级策略**。InjecAgent [59] 和 ASB [60] 衡量模型在实际 API 前被装入工具调用的程度；ToolEmm [40] 衡量仿真器能否在被提示实际 API 前发出有害调用。Progenty [46] 以明确有害请求评分 agent 是否将合规。SMT 界限策略更新。Nemo Guardrails [38] 拦截对话动作以应对可编程策略；OWASP 的 LLM Top 10 结果失败 LLM06 过度代理 [36]。差异：那些系统决定是否允许调用。我们决定调用是否会关闭，且那个关闭可能关闭。表 4 是我们搜索的网格；那些基准重叠 A4 和部分 A5。

**安全编排与工作流批准**。SOAR 平台拥有自动多厂商响应 [26]，包括人类批准任务、playbook 版本化和带幂等性的重试键 [37]。Bridges 等人 [10] 在 24 个中使用了六个，且发现工单准确性下降甚至效率收益。差异：那些将 playbook 语义作为 ground truth——如果 containment 步骤返回成功且 playbook 说工单可以关闭，它关闭——并且它们将一个步骤绑定到工作流实例，而非将被分发的内容绑定到该步骤。Playbook_semantic 臂衡量那个 closer，不是商业产品：Suite A 仍关闭 8/8，且每个弱回执 A1/A5 单元格匹配 naive 的未中介关闭。我们不评估 Cortex、XSOAR 或任何命名 SOAR 设备。假设正是不受信规划者写入的；§9.10 显示得到绑定正确如何容易，即使你知道。

**提交协议、回执与长时间运行的工作**。提交/提交差异和回执的处理作为远程效应的唯一可接受证据是数据库民间传说 [21]，跨服务观察的工作必须是幂等的并在分布式事务中重调和 [24]。Sagas [18] 是我们保留两个工作的方式；事务发件箱 [39] 是一个崩溃不能丢弃的地方。Merkle 的内容寻址提交 [32] 是什么使我们在运行时监视器能保证的上限中，我们将其作为我们在经典设置中保持的；Schneider 的 EM 可执行策略 [45] 是可信报告自己状态的组件，因为该组件报告结果是我们在对抗控制下的；"prepared" 是一个被验证的声明而非信念协议消息，我们关心的失败是安全违规而非卡住的事务。

**SOC 中的语言模型**。SOC 工作本身就是一种可用性和过程文学 [20, 29, 49]，早在它是语言模型之前。近期工作评估 SOC 上的 agent 和模型：多智能体事件分析证据 [54]、恶意软件分析 [52] 与威胁情报推理基准 [14]，以及 agent 化的分析师能力 [27]。本文中的规划者是 ReAct shape [58]，工具 [44] 是顶层策略 [38, 46]，看起来像邻域但不是。差异：所有那些得分系统分析质量；没有一个让系统改变世界，因此它们都不能报告错误关闭或泄漏，且指标与我们的不构成；我们在同一表上保持两者关闭。

## 12 结论（Conclusion）

分析可能出错；外部世界和发生了什么的记录可能不是。使 close、dispatch、verify 和发件箱写回取决于证据，规划者撰写该证据不足以将其区分为代码。我们通过边界注入而非询问门函数的判决来评估它，那告诉我们无论代码在做什么：四个可切换中介器和角色拆分未卸载，57 个注入产生了 47 个危害，两者都加载了，两者都没有。伪 live 列为 0/29。一个规划者登录不能写 CLOSED、发件箱、批准、动作状态或删除事件。属性准入在同四个点遗留 16/45 残差（HMAC 上的同两文档留 16）；那些是 II 的测量，不是引理的证明。kind 实例中，stock-API 子集是 8/8、6/8 属性、0/8 TEI；仍映射的 tei.lab 子集是 3/3、3/3、0/3（未复现于原始产品，未合并）。TEI.java TLA 对有限片（Java TLC，10800 不同状态）无反例，不是实现的证明；AttributeOnly 不对 close 和绑定 CEs 无反例；TEIPair 有视图关闭 CE。这些都不是保护域、生产集群或受版权保护的提示注入。它是写路径的完整性属性，实例化两次，由测量、指定和消融。
